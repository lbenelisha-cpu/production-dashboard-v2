# תיקון 502 — ניסיונות חוזרים ב-storage API

## הבאג

`index.html`, שורה 775 בגרסה המקורית:

```js
const attempts = action === 'get' || action === 'getMany' || action === 'status' ? 2 : 1;
```

לפעולות **`set`** ו-**`appendEvent`** הערך היה **1**.

מתחת, בלוק ה-catch כבר הכיל לוגיקת retry נכונה:

```js
const retryable = err?.name === 'AbortError' || [502,503,504].includes(Number(err?.status));
if(!retryable || attempt === attempts) throw err;
```

אבל עם `attempts = 1`, התנאי `attempt === attempts` מתקיים כבר בסיבוב הראשון.
**בלוק ה-retry היה קוד מת עבור כל פעולת כתיבה.**

העלאת קובץ האיכות הגדול מפורקת למאות קריאות `set`. Netlify Blobs מחזיר
502/503 חולפים תחת עומס — זה נורמלי. 502 בודד על מקטע אחד הפיל את כל
ההעלאה, ללא ניסיון שני.

זה מסביר למה זה נכשל דווקא על הקובץ הגדול: ככל שיש יותר מקטעים, הסיכוי
שלפחות אחד יקבל 502 שואף ל-1. בקבצים קטנים אותו באג פשוט לא מתבטא.

בצילום הרשת שלך: 2 קריאות `storage` ב-502, כל השאר 200.

## התיקון

1. **ניסיונות חוזרים לכל הפעולות** — `STORAGE_MAX_ATTEMPTS = 5`, כולל `set`.
2. **השהיה מעריכית עם jitter** — 500ms, 1s, 2s, 4s (תקרה 8s) ועוד 0-300ms
   אקראי. ה-jitter חשוב: בלעדיו מקטעים מקבילים מנסים שוב בו-זמנית ומחזירים
   בדיוק את העומס שגרם ל-502.
3. **הורחבה רשימת השגיאות החולפות** — נוספו 429 (rate limit), 500, וכשל רשת
   של `fetch` (נזרק כ-`TypeError`, שקודם לא נחשב ל-retryable).
4. **הודעת שגיאה שימושית** — אחרי מיצוי הניסיונות ההודעה כוללת את הפעולה,
   קוד הסטטוס ומפתח המקטע שנכשל, במקום "storage api error 502" גנרי.

## התקנה
החלף את `index.html` בשורש הפרויקט ופרוס מחדש ל-Netlify.
זה הקובץ היחיד שהשתנה.

## שים לב — שתי בסיסי קוד שונים
האתר `adama-pro.netlify.app` מריץ את `index.html` המונוליטי (v4.6.4,
Netlify Blobs, `xlsx.full.min.js` כתג script).

הפאצ'ים הקודמים בשיחה (12.9.0 / 12.9.1 / 12.9.2) מתקנים את
`src/DashboardApp.jsx` — פרויקט React/Vite מול Supabase. **הם לא נמצאים
באפליקציה שרצה כרגע.** אותה בעיית 502 קיימת שם בצורה אחרת: `cloudData.js`
כן מיישם retry (`MAX_RETRIES`, `retryable()`), כך שהיא פחות חשופה.

התיקונים לכרטיס המנה (הדדופליקציה שמחקה מדידות, החלטת השימוש, הפרדת
ה-Lots) רלוונטיים רק לפרויקט ה-React. `index.html` הזה אפילו לא מכיל
"כרטיס מנה".

# עדכון — השגיאה "הקובץ לא זוהה כקובץ סיכום איכות או כקובץ תוצאות בדיקה"

## מה נבדק
חילצתי את קוד הפענוח מ-`index.html` v4.6.9 (`classifyQualityWorkbook`,
`mapQualityHeaders`, `processQualityResultsWorkbook`, `QUALITY_HEADER_MAP`)
והרצתי אותו כמו שהוא על הנתונים האמיתיים.

**על חלק מפוצל של 15,684 שורות — עם כותרות זהות לחלוטין לקובץ הגדול:**
```
classifyQualityWorkbook -> { hasResults: true, hasSummary: false }   ✔
processQualityResultsWorkbook -> 15,684 שורות                        ✔
```
מיפוי הכותרות תקין: batch, inspection_lot, measured_value, lower_limit,
upper_limit, result_status, ud_code, sample — כולם נמצאו.

**כלומר הפורמט של הקובץ תקין והפענוח יודע לקרוא אותו.** הבעיה היא הגודל:
על הקובץ המלא (281,308 שורות) אותו קוד בדיוק, עם תקרת heap דמוית-דפדפן
של 2GB, לא סיים תוך 10 דקות.

## למה ההודעה הטעתה
`classifyQualityWorkbook` בולע שגיאות:
```js
try{ grid=XLSX.utils.sheet_to_json(ws,{...}); }catch(e){ continue; }
```
כשהפענוח נופל מחוסר זיכרון, `hasResults` ו-`hasSummary` נשארים `false`,
שני הפרסרים רצים ומחזירים 0, והקוד זורק "הקובץ לא זוהה". שגיאת פורמט
במקום שגיאת זיכרון — בדיוק אותה תבנית שראינו בפרויקט ה-React.

## מה תוקן

### א. מגבלת שני קבצים הוסרה
```js
if(files.length<1 || files.length>2){ ... }   // קודם
```
ייצוא גדול חייב להיות מפוצל, ואז יש 9-12 חלקים. עכשיו אפשר לבחור עד 20
קבצים בבת אחת.

### ב. צבירה במקום דריסה  ← קריטי
```js
qualityTestResults = resultRows;   // קודם — כל טעינה מחקה את הקודמת
```
זה אומר שטעינת חלקים בזה אחר זה הייתה משאירה רק את החלק האחרון. עכשיו כל
חלק מתווסף לקודמים עם סינון כפילויות (כולל `sample` במפתח, כדי שמדידות
חוזרות של אותו מאפיין לא יימחקו — אותו באג שתוקן בפרויקט ה-React).
אותו תיקון הוחל גם על `qualityEntries`.

### ג. הודעת שגיאה כנה
קובץ מעל 15MB שנכשל בפענוח מקבל עכשיו:
*"הקובץ גדול מדי לפענוח בדפדפן (40MB). פצלו את הייצוא מ-SAP לפי חודש
וטענו את החלקים יחד."*
"לא זוהה" נשמר רק למקרה שהכותרות באמת לא מוכרות.

## איך להשתמש
1. פרוס את `index.html` המתוקן.
2. לחץ "טעינת איכות" ובחר את **כל 9 החלקים המפוצלים יחד** (Ctrl+A בדיאלוג).
3. הם ייטענו ויצטברו ל-281,308 השורות המלאות.

# עדכון — מנה עם החלטת שימוש שמציגה "אין תוצאות בדיקה"

## מה קרה במנה 0000008171
חיפשתי בנתונים האמיתיים. **התוצאות קיימות:**

```
16 שורות · Batch 0000008171 · Inspection Lot 40000270588 · מק"ט 10000000451
כולן בקובץ quality_2026-08.xlsx
DENSITY 20°C · PH 1% · TZLILUT(TRANSP) · FLUROCHLOR ASSA · TOLUENE ·
HUMID K.FISHER · EMULSION 120MIN · בדיקת עקבות · בקרות טכנולוגיות ועוד
```

הן פשוט לא נטענו למערכת.

## למה זה נראה כאילו הכול נטען
בבחירה של שני הקבצים יחד, קובץ החלטת השימוש (1.1MB) נקרא בהצלחה וקובץ
התוצאות (40MB) נפל. הקוד בדק:

```js
if(!summaryRows.length && !resultRows.length){ throw ... }
```

**רק אם שניהם ריקים.** מכיוון שהסיכום הצליח, לא נזרקה שגיאה, הוצגה הודעת
הצלחה, וקובץ התוצאות נבלע בשקט. משם כל מנה נראית "מאושרת אבל בלי תוצאות".

זה גם מסביר למה ביומן הטעינות הופיעו רק 2 קבצים ולא 3: קבוצת "תוצאות
בדיקה" נשארה ריקה כי אף קובץ תוצאות לא נטען בפועל.

## מה תוקן
1. **דיווח לכל קובץ בנפרד.** קובץ שנבחר ולא תרם ולו שורה אחת מזוהה
   ומדווח בשמו:
   *"1 מתוך 2 הקבצים לא נטענו: 8e71de11-….xlsx (40MB) — גדולים מדי
   לפענוח בדפדפן. פצלו לפי חודש וטענו את החלקים יחד."*
2. **קבוצה רביעית ביומן — "⚠ קבצים שנבחרו ולא נטענו"**, באדום, עם שם
   הקובץ והשעה. אי אפשר יותר לפספס שקובץ נפל.
3. **טעינה מוצלחת מנקה רישום כישלון קודם** של אותו שם קובץ, ולהפך.
   אומת בבדיקה.

טענו את 9 החלקים המפוצלים יחד. במיוחד `quality_2026-08.xlsx` — שם יושבות
16 התוצאות של מנה 8171.
